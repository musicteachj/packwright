# Plan: Packwright as an MCP server

> Written and approved on 2026-10-10; James's decisions are recorded below. The idea and the reasons are in
> `docs/ideas/2026-10-08-mcp-server.md`; the experiment that cleared it is `docs/experiments/2026-10-09-mcp-without/`.
> Deployment is on hold by James's decision of 2026-10-10, so this plan builds everything that can be built and
> tested locally, and stops short of a public address.

## What this builds, in one paragraph

A person chatting with an AI asks about a label. Their AI calls Packwright's `/mcp` address with the label's
details; Packwright draws the label, runs the same rules the website runs, and answers with every finding, its
citation, and the checks that did not run. The AI explains the answer. No AI runs inside Packwright on this path,
and nothing is saved. The work is four stages: **one shared judge** in `label-core` that the website and the server
both call, so they can never disagree; **one shared input schema**, so they refuse the same documents; **the
server**; and **the full with/without evaluation** that measures what the tool changes.

## What the plan rests on — read on 2026-10-10

**The website's report today** (mapped from the code, and the two load-bearing claims re-read by hand):

- Two places judge a label, both in the browser: the editor store (`apps/web/src/stores/labelDocument.ts`) and the
  audit report (`apps/web/src/audit/report.ts`). Both lay the label out, call `runRules`, call `declinedChecks`,
  build a "cannot be checked" list with `uncheckableIn` (`apps/web/src/uncheckable.ts`), and group by severity.
  The live API runs no rules; it lays out and renders PDFs. The one caller of `runRules` in `apps/api` is the
  experiment harness (`experiments/withoutTool/prompt.ts`), which records the engine's findings beside each case.
- **One sentence of report text is written in the web app, not the engine**: `uncheckableIn` composes "Artwork is
  printed over the … symbol. A symbol with ink through it will not scan whatever its margins measure." A server
  that did not share it would say something different about the same label.
- Severity grouping and the failures/passes split are written twice, once in each of the two places.
- The editor validates nothing against the API's zod schemas; the API canonicalises and de-duplicates GHS codes and
  refuses codes with no verified text. The schemas live in `apps/api/src/labels/schemas.ts`, which imports
  `EMBEDDED_FONT_FAMILIES` from `renderPdf` and through it PDFKit and Node — so they cannot move into `label-core` as
  they stand.
- `label-core` has the pieces a judge needs and no judge: `runRules`, `declinedChecks`, `withholdUncertifiablePasses`,
  `listRules`, `citationsOf`, `codesOf`, `severitiesOf`, `hazardStatementText`, `precautionaryStatementText`,
  `isValidCheckDigit`, `calculateCheckDigit`. UPC-A layout needs bwip-js handed in; its `BwipRenderer` type is not
  exported, and both apps cast to it.

**MCP as it stands** (registry, type declarations in the published tarballs, and the docs, all fetched today):

- The specification is **2026-07-28**, which removed sessions and the `initialize` handshake. A tools-only server
  needs no SSE of its own.
- Packages, all ESM, Node ≥ 20: `@modelcontextprotocol/server` **2.3.1** (2026-10-05; zod `^4.2.0` as a dependency),
  `@modelcontextprotocol/express` **2.0.2** (Express `^4.18 || ^5` as a peer), and `@modelcontextprotocol/node`
  **2.1.1**, which mounting on Express also needs. The repo's zod 4.4.3, Express 5.2.1 and Node 24 all fit.
- The API, confirmed in the declarations: `createMcpHandler(factory, { legacy: 'stateless' | 'reject', … })` builds
  a fresh `McpServer` per request; `McpServer.registerTool(name, { title, description, inputSchema, outputSchema,
  annotations }, handler)`; `toNodeHandler` mounts it on Express; `hostHeaderValidation` and `originValidation`
  guard it on an existing app.
- **Claude's connector client still speaks the older, `initialize`-era protocol**, which the default
  `legacy: 'stateless'` serves; `'reject'` would lock Claude out. Older clients are answered as SSE whatever the
  response mode, which is fine for Claude and needs checking against the load balancer's idle timeout at phase 8.
- Claude custom connectors need public HTTPS, accept servers with **no sign-in**, cap a tool result at about
  150,000 characters (Claude Code at 25,000 tokens) and a call at 240 s, and arrive from **one Anthropic address range, `160.79.104.0/21`** — so a
  per-IP rate limit would treat every claude.ai user as one caller. Claude's docs warn that over-strict `Origin`
  checks and 403/429 answers break connectors. Read-only tools should carry a `title` and `readOnlyHint: true`.
- Testing: the SDK's own client can call the handler in-process from Vitest, in either protocol era; MCP Inspector
  2.10.1 (`npx @modelcontextprotocol/inspector --cli … --strict`) checks schemas from outside.

<https://ts.sdk.modelcontextprotocol.io/v2/serving/express.md>, <https://ts.sdk.modelcontextprotocol.io/v2/servers/tools.md>,
<https://ts.sdk.modelcontextprotocol.io/v2/testing.md>, <https://claude.com/docs/connectors/custom/add-unlisted.md>,

## Stage 16 — the shared judge, in `label-core`

**Goal:** one function that turns a label document into the report, called by the editor, the audit screen and the
server, so the three can never give different verdicts.

**As built on 2026-10-10** (PR #79) — the shape the server's output schema is written from. The first sketch here
took the encoder as a second argument and called the grouping `bySeverity`; neither survived.

```ts
judgeLabel(request: JudgeRequest): LabelJudgement      // lays out, then judges, or refuses
judgeLayout(context: RuleContext): Judgement           // judges a layout in hand — the editor's path
layOutLabel(request: JudgeRequest): ResolvedLayout     // the one dispatch from label type to engine

type JudgeRequest =
  | { labelType: 'gs1-retail'; data; stock; barcode: BarcodeEncoder }
  | { labelType: 'ghs-chemical'; data; stock }
  | { labelType: 'us-food'; data; stock }
```

**The encoder is required for a UPC-A label** — in the type, so a caller cannot forget it — and a UPC-A request
that reaches the judge without a usable one at runtime is `refused`, never judged: a judgement made with no symbol
drawn could pass barcode rules on a barcode that was never printed. So is an unknown label type, and a symbol the
encoder could not produce. The judge does not re-check the document's shape; the schema of stage 17 does that at
the server's door.

`LabelJudgement` is either `{ outcome: 'refused', reason }` or `{ outcome: 'judged', layout, findings, declined,
groups, failures, passes, blocking, uncheckable }`, all read-only, in the order and with the exact content the
website showed before.

- **Moves into `label-core`:** `uncheckableIn` and its overprint sentence; the severity grouping and the
  failures/passes split (written once instead of twice); `hasBlocking`. The `BwipRenderer` type, declared twice today
  (`layout/engine.ts`, `symbology/layOutSymbol.ts`), becomes one exported `BarcodeEncoder`, and the web app's own
  local type of that name gives way to it. **Exporting it is not enough on its own**: bwip-js's published types do
  not match the interface, which is why seven call sites outside the tests cast, and they need three different
  fixes. Four in the apps — `apps/api` `labels/routes.ts`, `labels/printTestSheet.ts` and
  `experiments/withoutTool/prompt.ts`, and the module load in `apps/web/src/barcodeEncoder.ts` — go through one
  typed adapter from bwip-js to `BarcodeEncoder`, which lives in the apps because `label-core` does not import
  bwip-js. The fifth, `verifiedSpanOnly` in the same web file, is a hand-written stand-in renderer rather than
  bwip-js, and is simply declared as a `BarcodeEncoder`.
  `label-core`'s `layout/engine.ts` casts between its own two declarations, and merging them removes it.
  `rules/fixtures/sweep.ts` takes `bwip: unknown`, and is retyped to take a `BarcodeEncoder`. **As built
  (2026-10-10): no adapter was needed.** The mismatch was the options parameter — `Record<string, unknown>` against
  bwip-js's `RenderOptions`, which requires `bcid` and `text` — and declaring `BarcodeRenderOptions` as exactly the
  four options the engine passes made bwip-js satisfy `BarcodeEncoder` as it is, so all seven casts were removed
  outright.
- **The experiment harness moves onto it too**, so stage 19's "with" half and the recorded "without" half are read
  against the same judgement: `prompt.ts` calls `runRules` alone today, without `declinedChecks`.
- **Stays in the web app:** encoder gating (a server always has the encoder), the rail's summary sentences and
  counts, the ANSI words and icons, field focusing, and the audit's `unconfirmed` list — presentation, or facts
  about a photograph rather than about a label.
- **The proof that nothing changed:** before touching the store, a test captures what today's two code paths report
  for every fixture and every permission document the sweep already builds; `judgeLabel` must reproduce it exactly,
  finding by finding. Then the store and the audit report switch to it and their own tests stay green.
- **Size:** about 500 lines of code and 400 of tests, the adapter and its seven call sites included. **Review:** `medium` per commit, `high` on the PR — it is the
  path every verdict will travel. **Mutation tests:** the overprint sentence, the grouping order, the withholding, and the refusal of a UPC-A label
  with no encoder.

## Stage 17 — one input schema, shared

The server must refuse the same malformed documents the export routes refuse, in the same words. So the label
document schemas move from `apps/api/src/labels/schemas.ts` into `label-core` (which already lists zod and imports
no framework), after `EMBEDDED_FONT_FAMILIES` moves into `label-core`'s `text/` module where the face names belong;
`renderPdf` then imports it from there. The API's routes keep their behaviour and error format, and their tests stay
green unchanged. **Size:** mostly a move, about 300 lines. **Review:** `medium`, since behaviour must not change;
the existing route tests are the proof.

**As built (2026-10-10):** the schema is `packages/label-core/src/schema/labelDocument.ts`, imported as
`@packwright/label-core/schema` and **not** from the package root — its schemas are built when it loads, so the
root would have carried zod into the web bundle, which uses none of it. The face names are `EMBEDDED_FONT_FAMILIES`
in `text/faces.ts`, and the renderer's face table is keyed on their type. The schema's own `LABEL_TYPES` was a
second copy of the one in `rules/types.ts` and went. The proof beyond the route tests: eight malformed or
unexportable requests answer byte for byte as on `dev`. The backlog's `SymbolLayoutError` gap was folded in as a
second commit: the export routes now refuse it with the 422 they give a `LayoutError`.

## Stage 18 — the server, in `apps/api`

**Four tools, all read-only** (`readOnlyHint: true`, `openWorldHint: false`, a `title` each), agreed with James on
2026-10-10. Renaming one later would not break a connection — a client asks for the list of tools each time it
connects — but it would reset whatever refers to a tool by name, such as a user's "always allow" setting in Claude
and the evaluation harness, so the names are fixed here and changed only deliberately:

| Tool | Input | Answer |
|---|---|---|
| `check_label` | `labelType`, `data`, optional `stock` — the shared schema | The judgement: findings with severity, message, measurement and **citation as data**; checks that did not run, with what each needs; what could not be drawn; and always the sentence that **no findings is not a statement of compliance**, with the address of `WHAT-IS-NOT-CHECKED.md`. |
| `list_rules` | optional `labelType` | Every rule: id, title, citations, codes and their severities — the `/rules` page's data. |
| `ghs_statement_text` | `regime`, `code` | The verified text from the reference tables, or an explicit "no verified text for this code under this regime". **Never generated.** |
| `check_gtin` | `gtin`: 8, 12, 13 or 14 digits, the GTIN lengths — anything else is refused by the input schema before the tool runs | Whether the check digit is right and, if not, the right one — `isValidCheckDigit` and `calculateCheckDigit`, which take any run of digits of almost any length and throw on the rest, so the schema is what keeps a two-digit string from being called a valid GTIN. |

- **Mounting:** `app.all('/mcp', …)` ahead of the SPA fallback, with `hostHeaderValidation` for the public host
  and localhost, and `originValidation` with an explicit list. Its documentation says requests without an `Origin`
  pass, "non-browser MCP clients do not send one", and a present one not on the list gets 403 — while the
  specification says servers MUST validate `Origin`, and Claude's docs warn that an over-strict check rejects
  Anthropic's requests. **Whether Anthropic's requests carry an `Origin`, and which, is not documented anywhere
  read on 2026-10-10**; stage 18 settles it by logging what a real Claude Code connection sends before fixing the
  list, and the connector test at phase 8 confirms it for claude.ai. `legacy` stays `'stateless'`. The existing 256 kB JSON body limit applies; `maxToolInputElements` caps
  the size of one document.
- **Every answer carries both forms:** `structuredContent` validated against an `outputSchema`, and the same as
  text for clients that read only text. A judgement of the largest fixture is measured against Claude Code's
  25,000-token cap, the tighter of the two.
- **Not exposed:** saving labels, PDF export, and the photo audit — anything that writes, costs money, or runs a
  model.
- **An off switch:** `MCP_ENABLED` in `env.ts`, so `/mcp` can be turned off without touching the rest of the app.
- **Two rate limits, because claude.ai users share one address range.** Calls from Anthropic's range
  (`160.79.104.0/21`, from Claude's connector docs) share one allowance, and every other address has its own —
  about 60 an hour, for clients such as Claude Code that call from the user's own machine. A single per-address
  limit would treat all of claude.ai as one caller and cut it off at once. Answers past a limit are the standard
  429. **The shared allowance is still one bucket**, and Claude's docs say a 429 breaks the connector, so one heavy
  claude.ai user could cut off the rest until the hour turns; nothing tells claude.ai users apart without a sign-in.
  So that tier is set high — several thousand calls an hour, since a check costs a fraction of a millisecond on a
  laptop (measured 2026-10-10: 0.26 ms for the conformant food label) and no money — every refusal is logged, and
  the number is raised if it is ever reached. The numbers are starting points, tuned after launch. Stage 18 checks which Claude apps route through Anthropic and which call directly, and reads the
  caller's address the same way the existing limiters do, through `TRUST_PROXY_HOPS`.
- **Tests:** the SDK's client against the handler in-process, in **both** protocol eras (Claude uses the older);
  `check_label` on every fixture equals `judgeLabel` on it; refusal paths; each tool's schema passes Inspector's
  `--strict` check, run by hand and recorded.
- **Docs:** a short "Use Packwright from your AI" page — Claude Desktop, claude.ai, Claude Code
  (`claude mcp add --transport http packwright <url>`) — written now, published with the address.
- **Size:** about 500 lines of code and 500 of tests, so two PRs if it grows. **Review:** `high` on the PR — a public
  interface that returns verdicts.

**As built (2026-10-10):** the packages were unchanged since the plan and are pinned exactly. What re-reading
and running them settled:

- **`check_label` is advertised as one object and validated as the union.** The shared schema is a union at its
  top, written `oneOf`, and Claude Code dropped the tool: "Skipping tool "check_label": its input schema uses
  top-level oneOf, which the Anthropic API does not accept" (its debug log). Neither the SDK nor Inspector's
  `--strict` objected; only connecting a real client found it. The model now reads `LabelCheckRequestOutline` —
  the same request with the union moved into `data` — and requests are still checked by `LabelCheckRequest`, so
  refusals keep the export routes' words. A test holds every tool's input to a plain object at the top.
- **Claude Code sends no `Origin`** and speaks protocol `2025-11-25`, the older era, observed by connecting
  Claude Code 2.1.169 to a local `/mcp`. What claude.ai's connector sends is still unknown; every `Origin` is
  logged, and the phase 8 checklist in `docs/DESIGN.md` reads it.
- **Routing:** claude.ai, Desktop, mobile and Cowork reach a connector from Anthropic's infrastructure; Claude
  Code connects from the user's machine (Claude's connector docs, re-read). The outbound range is IPv4 only.
- **Inspector `--strict`** passed all four schemas — it checks type arrays, remote `$ref`s and unconstrained
  schemas, so it is a narrower check than its name suggests.
- **The largest answer** among the 83 judged sweep documents is 24,775 characters with both forms included,
  about a third of Claude Code's 25,000-token cap even at three characters a token.
- The conversions and the check request moved into `label-core` first, as their own commit, so the server and
  the exporter cannot convert a label differently. The how-to page is `docs/USE-FROM-YOUR-AI.md`.

## Stage 19 — the full with/without evaluation

The experiment of 2026-10-09 measured the "without" half. This stage adds the "with" half on the same twelve
labels, the same three runs and the same rubric: the model gets the four tools and the same question. Locally,
before any deployment, the tools are offered to the model as ordinary tool definitions executed by the harness
against the in-process MCP handler — so the model sees what an MCP client would hand it, without a public address.
**Both halves run afresh, not just the "with" half.** Since stage 12 the engine prints "Includes 0g Added Sugars",
indented, so the four food prompts generated today differ from those sent on 2026-10-09 — the harness's guard
refused to regenerate them over the recorded answers on 2026-10-10, as it should. Pairing new "with" answers with
old "without" ones would compare two different labels, so stage 19 starts a new record beside the old one. Expected
cost: about $5–8, capped. The result is the evidence the idea doc asked for: what the tool changes in
citations, misses and false clearances. **Review:** `medium`; grading as before, by agents on a fixed rubric, with
the lead checking every fabricated citation and a sample of the rest.

## Decided with James, 2026-10-10

1. **Public**, with the two rate limits and the off switch above. Private would mean building an OAuth sign-in:
   on claude.ai the only standard private option is OAuth, and a simple shared key is a beta for a limited set of
   organisations (Claude's connector authentication docs, read 2026-10-10). Local only would leave nobody able to
   try it. Public adds no new kind of access — the website already checks any label for anyone — and **no AI cost to
   James**: Packwright calls no model on this path, the user's own assistant does the thinking on their own plan,
   and the photo audit, the one feature that spends James's key, is not offered here.
2. **The two-tier rate limit** in stage 18, numbers to be tuned after launch.
3. **The four tools** in stage 18, as named.
4. **Stage 17 before the server**, so the export routes and the server refuse the same documents in the same
   words.

## Risks

- **A wrong answer here hurts the one project whose value is being right.** Hence one judge, and an answer that
  always says what was not checked and that no findings is not compliance.
- **The protocol is new and moving**: the specification is ten weeks old and the SDK major version recent. Pin
  exact versions, and re-read the docs at stage 18 rather than trusting this page.
- **A model can still misread a correct answer** — Packwright cannot stop that, only make every citation arrive as
  data the model has no need to invent.
- **Must not delay deployment once the hold lifts**: stages 16 and 17 are worth having even if the server never
  ships. Stages 18 and 19 depend on the protocol — 19 runs its tools through the in-process handler — and if the
  server is set aside, 19 still runs, offering the model the same four tools backed by `judgeLabel` and the
  reference tables directly, which measures the same thing without the transport.
